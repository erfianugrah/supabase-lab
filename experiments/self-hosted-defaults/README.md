# self-hosted-defaults

A local rig for the 2026 defaults of the self-hosted Docker stack (`docker/` in
the public supabase/supabase repository), checked against a running stack
rather than against its compose file. No Supabase project, no PAT, no cloud
spend: the stack runs in Docker on the machine that runs the tests.

| Module | Asks |
|---|---|
| SD01 | Is the gateway Envoy, with no Kong service and nothing on host port 8443? |
| SD02 | Do `sb_publishable_` and `sb_secret_` keys pass through Envoy, and as which role does PostgREST see them? |
| SD03 | Is the database Postgres 17, and is `pg_graphql` really off on a fresh stack? |
| SD04 | Do Studio and postgres-meta connect as `postgres`? |
| SD05 | Do analytics and vector exist only with `docker-compose.logs.yml`? |
| SD06 | Does `API_EXTERNAL_URL` carry `/auth/v1`, and is SAML served at `/auth/v1/sso/saml/*`? |
| SD07 | Control: with the Kong override, do the 8443 and `server`-header probes of SD01 see Kong? |
| SD08 | What does Envoy do with `sb_` keys when the four opaque-key variables are empty? |
| SD09 | Do the `sb_` keys work for Realtime (raw socket, supabase-js, private channels, REST broadcast)? |
| SD10 | Do the `sb_` keys work for Edge Functions, with `FUNCTIONS_VERIFY_JWT` false and true, and what does a function receive? |
| SD11 | Does `utils/upgrade-pg17.sh` take a Postgres 15 data directory to 17 with the data intact, and does the guide's rollback work? |
| SD12 | Do the default services start and answer from their linux/amd64 images (emulated on arm64)? |

Results and what was not measured: [RUNLOG.md](RUNLOG.md).

## Run

```sh
make stack     # clone supabase/supabase at the pinned commit into work/, copy docker/ to work/stack, generate secrets and keys
make up        # docker compose up -d --wait   (host ports 8000, 5432, 6543 must be free)
make probe     # SD01..SD08, writes evidence/<timestamp>/ (gitignored)
make clean     # down -v for every override, remove bind-mounted data, delete work/stack and its .env
make unit      # offline tests for lib/rig.ts
make publish-evidence RUN=evidence/<ts>/run-<stamp>.json   # redacted copy into out/<date>/
```

A second stack can run beside any other on the machine:
`make stack up probe SLOT=b GW_PORT=8200 PG_PORT=5632 TXN_PORT=6743` uses
`work/stack-b`, compose project `sd-b`, those host ports, and no fixed
container names (see the Makefile comment). SD11 starts from
`make stack up-pg15 SLOT=...`; SD12 from
`make stack amd64-layer pull up SLOT=... LAYERS=amd64`, which runs the core
services from their linux/amd64 images by digest. `make clean SLOT=...`
removes a slot stack.

`ONLY=SD01,SD04 make probe` runs a subset. SD05 to SD08 change the stack
(logs override, SAML, Kong swap, `.env` rewrite); they run after SD01 to SD04
in id order, and SD06d (the SAML-disabled default) skips on a stack where SAML
was already enabled, so start from `make clean stack up` for a full run.

Secrets are generated by the upstream `utils/*.sh` scripts into
`work/stack/.env` and are never printed; every result string goes through
`scrub` in `lib/rig.ts`.

## Layout

- `tests/sd*.ts` - the modules.
- `lib/rig.ts` - stack access, HTTP, `docker`/`docker compose` wrappers, secret scrubbing, container names on a SLOT stack.
- `lib/amd64-layer.ts` - writes SD12's compose layer (amd64 images by manifest digest).
- `compose/docker-compose.saml.yml` - the SAML override SD06 applies (the guide edits `docker-compose.yml` instead).
- `work/` - gitignored: the pinned clone and the stack copy.
